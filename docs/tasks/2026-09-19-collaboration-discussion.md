# 2026-09-19 开发协作讨论结论

## 已确认的工作方式

飞书口头需求先结合项目整理目标、范围、业务问题和验收条件，再形成 Issue。准备好的任务加 symphony:ready，由 Symphony 在独立目录实现、自检并交付草稿 PR。之后独立 review、人工验收，再由负责人决定合并和部署。

Review 检查代码缺陷、需求遗漏、权限和验证证据；人工验收检查真实页面和业务效果。合并不等于部署。需求讨论会话可审查由 Symphony 编写的代码；若同一会话承担实现，建议换审查上下文。

## 已核实的能力

当前工作流不自动启动独立 reviewer，不自动合并或部署。2026-09-19 检查 GH-1 会话记录时模型为 gpt-6-astra，容器未显式固定模型；这不是永久默认值保证。

## 按复杂度分配模型

建议在 Issue 准备阶段评估复杂度与风险，并记录模型选择理由：简单文案/样式使用快速模型及低思考；普通交互/接口使用常规模型及中思考；权限、迁移、并发或复杂重构使用强模型及高思考；高风险任务增加独立审查。允许用户明确覆盖。

讨论时这只是方案。2026-09-19 已落地 GPT 模型与思考深度标签路由，缺省为 gpt-6-astra / low，准备 Issue 时由 Agent 选择并校验；操作见 [Symphony 手册](../15-symphony.md)。真实远端测试 Issue 验收待授权，尚未实现自动升级或第三方模型。升级仍需次数/成本边界；缺需求和环境问题需报告，不能无限换模型重试。第三方模型需要对应凭据、协议及工具调用验证，不能仅凭普通聊天可用判定兼容。
