> 历史评审：本文评审的是旧云对象存储、昼夜和七表候选方案。2026-09-16 起采用[内网本地存储基础设施](10-local-infrastructure.md)，本文结论不作为当前实现要求。

当时的方案适合作为 V0.1 的评审基础，但还不适合直接按全部候选契约展开开发。主要问题集中在文件交付方式尚未确认、数据库写入职责不够明确，以及管理流程缺少部分查询入口。

整体没有明显的架构过度设计。局部存在提前实现通用资源管理的风险，也存在已经设置较多数据库防护、却尚未覆盖实际调用边界的情况。判断一项防御是否值得，应同时考虑当前是否存在触发路径、出错后的影响，以及保护措施自身的实现和维护成本。

本次审查覆盖架构、SQL、契约生成源、工作流和验证脚本。P1 表示相关模块实现或上线前需要解决；P2 表示需要明确处理方式并补充验证。设计待定、条件性风险和已复现行为分别标注，不能把它们都视为已上线漏洞。

1. **P1 · 文件交付方式是当前实现前置条件，候选结构不应成为默认需求。**

   [数据库说明](02-data-model.md)已经明确，`version_asset`、`logical_path`、跨版本复用和依赖检查尚未定稿，这个边界合理。但候选 SQL 和契约已经包含三个平台、多种素材类型、入口关联和最多 1,000 个文件。开发时若直接依据契约生成完整管理功能，容易在没有真实成品的情况下实现一套资源管理系统。

   应先完成一个目标平台的真实成品加载：上传交付物、取得清单、下载、播放、重新定位和回滚。根据样例决定每个平台登记一个完整包，还是登记入口及必要依赖。继续保留场景、内容版本和成品文件的分离；文件数量与关联形式由实际加载方式决定。无需为了简化而强行合表，也无需为了未来扩展实现包内资源编辑、通用依赖图和跨版本去重。

   这是设计决策尚未完成，不是现有多文件候选模型已经被证明错误。验收依据应是样例目录、加载说明、包体大小和一次真机加载记录。

2. **P1 · 发布函数不是目前 SQL 强制要求的唯一写入入口。**

   [V002](../database/migrations/V002__publication_functions.sql)在 `publish_version` 内完成并发检查、发布和审计；[V001](../database/migrations/V001__platform.sql)的场景触发器只检查目标版本能否使用，没有强制要求调用发布函数，也没有在直接修改指针时检查操作人或递增 `lock_version`。

   隔离测试创建了普通数据库角色，授予读取表、更新 `scene` 和新增 `audit_log` 的权限。该角色可以直接切换到另一个 `READY` 版本，同时不产生发布审计、不递增场景版本号。它还可以通过插入一条 `PUBLISH_VERSION` 日志，使从未发布的版本通过 `version_was_published` 检查。测试未使用超级用户执行这两项操作，但这些授权是测试中构造的；仓库尚无实际运行账号的授权配置。

   这说明数据库保护具有明确的适用边界：正常调用函数时能保证事务一致性，拥有相应表写权限的其他调用路径仍能绕过。应用尚未实现，因此不能据此认定游客能够攻击系统。

   实现前应确定关键状态由谁写入。若继续由数据库函数负责发布，应配套限制运行账号直接修改发布字段及写入发布事实的权限，并确保函数在受控权限下仍可正常执行。若由应用事务负责，则应把统一服务入口、操作人来源、并发检查和审计作为应用的明确职责，避免文档暗示数据库已经独立保证全部行为。迁移账号与运行账号应分开，权限测试使用实际运行角色。

   冻结同样需要检查写入入口。只追加审计可以防止普通更新和删除，并不自动证明每一条新增记录都来自真实业务操作。

3. **P2 · 管理接口缺少标记查询，页面重载后无法完整恢复操作上下文。**

   [契约生成源](../scripts/generate_contracts.py)提供创建标记和启停标记，却没有标记列表或详情。`MarkerView` 只返回 ID、入口码和场景 ID，无法查询启用状态、尺寸与安装参数。管理员关闭页面后，现有接口不能按场景重新找到标记并检查是否需要禁用或重新制作二维码。

   场景创建支持地址、经纬度和坐标类型，但 `SceneView` 不返回这些信息，管理员也无法核对录入结果。未关联版本的上传文件则只能凭已知 `assetId` 查询；一旦客户端没有保留 ID，就缺少管理端的恢复入口。

   建议先补按场景查询标记及其详情，并让场景详情返回已经支持录入的字段。上传记录可以按实际管理页面增加有限的状态查询，不必扩展成通用素材库。验收时用另一个管理员账号重新登录，在不依赖原浏览器本地缓存的情况下完成查询和后续操作。

4. **P2 · 冻结和发布函数会接受空的并发版本号。**

   [V002](../database/migrations/V002__publication_functions.sql)使用 `lock_version <> p_expected` 判断冲突。隔离测试确认，传入 SQL `NULL` 后，`seal_version` 和 `publish_version` 均可以执行成功，没有拒绝缺失的版本号。

   OpenAPI 已要求 `expectedVersion` 为必填整数；正确的 HTTP 参数校验可以阻止这类输入。这是数据库函数边界上的缺口，不能描述成已经存在的 HTTP 绕过。

   建议函数显式拒绝空值，或使用能够区分空值的比较方式，并保留应用层的参数校验。增加空值、过期值和正常值的测试即可。这项防御直接对应现有函数入参，修改成本较小，值得提前完成。

5. **P2 · JPA 与数据库对状态、版本号和关联集合的写入职责尚未约定。**

   架构选用 Spring Data JPA，但 [V001](../database/migrations/V001__platform.sql)在触发器中递增草稿的 `lock_version`，冻结后又要求除 `state` 外的所有字段保持不变。隔离测试确认，同时执行 `state='REVOKED'` 与 `lock_version=lock_version+1` 会被拒绝。

   如果应用随后把该字段直接映射为由 ORM 自动维护的版本号，并在撤销时一并递增，就会与触发器冲突。目前没有实体实现，因此这是已确认的 SQL 行为和有条件的集成风险，不是已发生的 JPA 故障。

   文件关联也只允许删除后新增，不能直接更新关联行。数据库函数修改状态后，应用还需要取得最新状态和版本号，避免继续使用旧实体返回响应或执行后续写入。

   建议只为这些关键操作建立明确的持久化入口，写清谁递增版本号、谁更新关联、何时重新读取结果。首个应用集成测试应包含保存草稿、替换同一路径文件、冻结、撤销和发布后立即查询。无需为整个项目建立复杂的通用持久化框架。

6. **P2 · 同步文件校验有合理边界，但目前的时限尚无实际包体支撑。**

   [工作流](03-workflows.md)暂定单文件 200 MiB、同时校验 2 个文件、总时限 120 秒，还要求绑定源对象版本、校验摘要、复制到最终位置、确认最终内容，以及超时后不得提交。防止文件被替换和请求重试出错是当前直传流程需要的保护，应当保留。

   但两个最大文件仅各完整读取一遍，就需要在 120 秒内传输 400 MiB，平均约为 3.33 MiB/s；这个估算尚未计入复制、最终确认和其他开销，不是容量测试结果。独立执行池如果没有限定等待队列，或者 HTTP 返回超时后校验仍占用连接和线程，也不能达到文档描述的行为。

   建议先按真实包体测量校验时长、峰值内存和存储读流量。采用流式读取、有限等待或直接拒绝、明确的存储请求时限，并让提交前的期限检查与本次校验身份保持一致。测试客户端重试、存储读取卡住，以及最终文件已经存在但数据库尚未登记的恢复路径。

   在样例验证之前，没有必要引入任务队列。若实际包体持续超出同步处理范围，可以先评审文档中已有的受控导入方案；这会增加另一条需要鉴权、审计和维护的入口，不应在尚无使用需求时同时实现。

7. **P2 · 曾经发布的事实与审计日志耦合，需要明确长期语义。**

   [V002](../database/migrations/V002__publication_functions.sql)从审计日志的 JSON 字段查询版本是否曾经发布。现有审计索引是 `(object_id, created_at)`，查询条件却是 `action` 和 `detail.versionId`，没有对应的过滤索引。数据量较小时未必构成性能问题，本次未进行负载测试，不能据此宣称接口已经缓慢。

   更值得先处理的是职责：日志内容同时决定公开访问资格，未来调整事件名称、导入日志或归档历史记录时，都可能改变业务行为。V0.1 已约定保留日志，所以归档造成的问题不是当前已发生的故障。

   如果业务只需要判断是否曾经发布，可以评估在版本上保留受控写入的首次发布时间，并由发布事务首次赋值，审计继续保存每次发布与回滚经过。这样不必新增发布服务或历史关系表，但必须同步调整冻结字段规则及写权限。若继续使用日志作为依据，则至少把发布事件格式、写入边界及查询方式固定下来；是否补表达式索引结合实际查询量决定。

   另外，当前接口只检查版本是否曾发布，没有区分请求者是否已经开始体验。因此，持有场景入口码和历史版本 ID 的新客户端，也能够请求有效历史版本。建议把下线说明写成“停止通过默认入口选择该版本，指定历史版本仍可访问”。如果这符合产品意图，就无需为区分新旧用户增加体验会话系统。

8. **P2 · 安全和运行要求已有方向，仍需转换为可执行的最小配置。**

   [接口与运行要求](04-api-security-operations.md)已经包含独立账号、Session、CSRF、密码哈希、私有对象存储、签名链接和备份恢复。这些都对应当前真实入口，属于合理防御。

   上线前仍需明确登录失败限制、Session 有效期、公开清单的请求限制、上传凭证可写范围，以及运行账号的数据库和对象存储权限。列出 `429` 状态码不等于已有请求限制。对象存储策略还应验证旧上传凭证不能修改最终文件；文件大小和类型限制需要在实际存储及服务校验中生效，不能只相信客户端提交的元数据。

   真机预览也需要一次完整联调。现有预览 API 要求管理员 Session，但尚未说明管理页面与 AR 客户端如何衔接。如果预览在同一登录客户端内完成，可以沿用现有方式；若需要跨设备传递访问资格，再针对该流程设计短期授权，不能直接开放未发布版本。

   运维上，先明确可以接受的数据损失时间和恢复时间，再执行一次数据库与对应文件的恢复演练。每日备份、暂不自动删除最终文件适合首期，但需要容量告警和受控临时文件清理。监控不必扩展成复杂平台，至少能发现校验阻塞、依赖不可用和备份失败。

以下设计建议保留或延后，判断依据是当前需求与实现成本。

| 设计 | 判断 | 原因及实施边界 |
|---|---|---|
| 单应用、按功能分包 | 保留 | 当前没有独立扩缩容或部署的需求 |
| 场景、内容版本、成品文件分离 | 保留 | 位置、一次内容快照和实际交付物有不同的变化周期 |
| 昼夜分别发布、指针回滚 | 保留 | 直接对应已确认的产品行为 |
| 冻结内容、不可覆盖的最终文件 | 保留 | 防止同一版本 ID 对应不同内容，支撑预览和回滚 |
| UUID、重复登记检查、短事务与并发检查 | 保留 | 解决重复点击、网络重试和多人发布的现有问题 |
| 独立账号、相同权限、操作审计 | 保留 | 满足责任追踪；暂无必要增加审批角色 |
| 单实例内存 Session | 保留 | 重启重新登录已明确，暂无必要引入分布式 Session |
| 多平台通用素材分类、依赖解析、跨版本复用 | 等真实交付物确认 | 需求未定，提前实现容易扩大范围 |
| 数据库触发器和应用校验 | 明确职责后保留必要部分 | 数据库保护稳定约束；应用校验输入和文件。相同规则不应在两处独立演化 |
| 自动物理清理、CDN、后台任务队列 | 依据实际需求再评估 | 先取得存储量、下载量和校验时长，再决定是否增加运维成本 |

七张表本身不能证明过度设计。更应关注是否让一个正常操作必须同时理解不必要的状态、函数、触发器、权限和多端协议。当前状态数量有限，冻结与回滚的职责也清楚；主要维护成本来自文件候选模型，以及 SQL 和未来应用之间尚未明确的写入边界。

实施顺序建议先确认首发平台和一个真实成品，同时明确发布及冻结的写入入口，再补齐管理查询与错误处理。随后完成登录、上传、冻结、真机预览、发布、扫码和回滚的一次完整流程。其他平台、文件复用与性能扩展依据这次验证结果安排。

本次数据库复验使用独立临时 PostgreSQL 18.4，原有 31 项检查通过，另外 5 项检查确认了上述边界行为，实例已停止。[审查证据](design-review-evidence.json)中的 `passed: true` 表示测试成功执行并确认所描述的行为，其中 `PROBE` 项确认的是风险行为存在，不表示设计没有问题。原有验证报告保持不变。

原有负向测试将任意 `psycopg.Error` 视为成功拒绝，建议后续核对预期错误类型，避免因其他 SQL 错误而误通过。SQL 当前大量使用默认异常，应用还需要稳定的业务错误映射，不能依赖异常文本判断所有 `409`。检查脚本对七张表的断言只适用于当前候选快照，不能成为后续文件模型调整的限制。

本次另外核对了三份生成产物与生成源的一致性、23 个接口操作及全部文档中的 36 个本地链接，并完成文风检查。当前 Python 环境缺少完整 Schema 校验依赖，本轮没有重新执行完整的 OpenAPI 和 JSON Schema 验证；原有契约验证记录不能代替应用测试。

目标 PostgreSQL 17 未在本机安装，本次结果不建立 17 的兼容性结论。当前没有 Spring Boot 应用，HTTP 鉴权、JPA 行为、对象存储策略、真实设备加载、容量及备份恢复仍需分别验证。
