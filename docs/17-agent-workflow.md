# Agent 工作流入口

本页供没有当前聊天记录的新 Agent 使用。先读根目录 [AGENTS.md](../AGENTS.md)，再按本页识别任务阶段。用户明确要求优先；已有授权持续有效，不重复索要。没有说明的业务目标不能靠猜测补齐。

## 根据用户的话选择流程

| 用户表达 | 当前 Agent 应做什么 | 本阶段交付 |
|---|---|---|
| “领导说要优化这个页面” | 看当前入口，询问影响范围和验收的关键问题；不直接编造方案或入队 | 已确认需求、待决问题 |
| “把这个需求整理成 Issue” | 按模板整理并按授权创建 Issue，准备适用检查和外置计划 | Issue、计划位置、检查范围；未授权执行则保持未入队 |
| “交给 Symphony/DeepSeek 做”或“开始执行这个 Issue” | 复用已确认需求，完成准备检查、模型校验和合同登记，再添加 ready | 可追踪的 Issue 和本轮执行记录 |
| 受控 Symphony 分配的编码任务 | 仅改约定代码和必要测试，完成后结束 turn，交给程序检查 | 工作区修改；最多响应一次程序发起的修复 |
| “审查 PR X” | 独立审查固定 SHA，执行适用本机检查，无阻断问题后提供实例 | 发现的问题，或健康的本机网址及验收交接 |
| “只审代码／不启动实例” | 按明确范围只审查 | 审查发现和验证边界 |
| “这个任务怎么停了／看看进度” | 只读状态和证据，解释失败或阻塞原因 | 当前状态、证据、可执行的下一步；不重试 |
| “修复这些反馈并重新执行” | 确认反馈范围、解决阻塞，通过显式恢复入口开启新一轮 | 保留历史的新 runId；重新验证新版本 |
| “合并／更新 Demo” | 进入另行授权的合并或部署工作，核对版本与目标环境 | 不属于本文的自动交付阶段 |

普通本地编码请求仍可按 [开发工作流](development-workflow.md) 本地完成；不能把所有新需求自动创建成 Issue。以上身份是流程职责，不表示必须创建新任务或启动子 Agent。需要独立审查时由实际独立的审查者接手，实现者不能自签。

## 从口头需求到可执行 Issue

1. **澄清需求。** 先读实际入口和现有行为；只询问会改变实现/验收的问题，例如谁使用、哪步不便、预期操作、要保留什么。记录已经确认的答案，给出建议时明确它还不是决定。领导的模糊口头意见不自动成为 Agent 可任意扩展的开发范围。
2. **写任务。** 按 [Issue 正文模板](examples/symphony-issue-template.md) 写目标、范围、验收和背景。大型需求先提出可独立验收的拆分方式。创建 Issue 和执行入队分别以用户请求是否已覆盖为准；已有明确执行授权时直接继续准备。
3. **预先确定检查。** 把每个验收条件对应到容器、本机或人工确认。容器只选 quick/frontend 和必要 Java 模块。宿主当前支持 smoke、scene-ui、accounts、ingestion，具体覆盖见 [本机手册](16-fast-review.md)。scene-ui 只覆盖场景页面，其他页面不能借用其通过结果；基础合成数据也不能代表所有功能的专用样本。缺检查器、浏览器环境、字体/系统库或合成数据准备方式时先在准备阶段解决，再入队。
4. **登记程序合同。** 从 [JSON 示例](examples/symphony-task-plan.json) 制作本任务的实际计划，字段为 title/profile/allowedPaths/javaModules/hostSuites/acceptance。宿主准备 Agent 运行 `scripts/symphony.ps1 PrepareTask -Issue N -PlanFile <实际文件>`，其中 N 和路径必须替换为真实值。程序合同保存在 `.local/symphony/data/task-control/GH-N/plan.json`，不是 Issue 正文或 Markdown 勾选。核对文件确实存在、内容与 Issue 一致；不能只凭没有 state.json 时的 TaskStatus 输出判断准备完成。
5. **校验并入队。** 按 [Symphony 手册](15-symphony.md) 的 Models/ValidateModel 校验用户指定或准备阶段说明理由的组合，设置 model/effort 标签，最后添加 ready。编码期间不换模型。涉及删除文件、符号链接或超过发布器大小上限时，先规划适用交付方式，不能让模型运行到最后才探索另一上传通道。

这部分由宿主准备 Agent 完成，不要求用户填写 JSON 或手动执行命令。程序计划只能登记已有检查能力；文字写了“需要检查某业务”不等于检查器已实现。

## 编码与程序收尾的职责

受控编码模型以工作流/适配器的明确标识识别身份，不因目录里存在 WORKFLOW.md 就认定自己已被调度。它只修改允许范围的源码和必要测试，不运行安装、构建、检查或 GitHub 写入，不修改计划/状态、不提交 Git、不操作本机验收环境。仓库通用验证要求由控制器执行，不能据此开始第二套检查。

模型结束 turn 后，固定程序检查：通过就交付草稿；首次代码失败允许一轮修复复验；再次失败、源码未变化的重复失败、环境/权限阻塞就停止。程序尽可能交付标明未通过的草稿；发布失败保留补丁、证据和工作区，不自动反复上传。标签更新失败不能绕过本地终态。

没有任务总时长/token 限制，只有单条命令等操作的超时。限制检查修复次数不代表会强制终止首次编码阶段的长时间思考；不要向用户承诺固定分钟数或所有形式的循环都已消除。安装/构建复用必须核对输入和产物，记录 executed/reused，源码或相关产物变化后旧证据不作新版本通过证明。

## 独立审查与本机交付

按 [审查规则](14-code-review.md) 和 [本机命令](16-fast-review.md) 执行：prepare 固定完整 SHA → 独立阅读需求和实际差异 → 无阻断问题后执行 check → serve → status 验证健康。hostSuites 从原计划/Issue 传入 `prepare --require-suite`；路径推断只是基础门槛，不替代业务判断。

实例仅使用随机回环端口、新数据库/账号/存储及合成数据。不得停止日常 Demo、使用日常账号或伪造登录。`--reviewed-sha` 是真实独立审查声明，不能当作启动工具所需的随意占位参数。

交付必须包括：完整 SHA、本机可用网址、凭据文件位置、已验证与复用的证据、待用户确认的具体操作/观感、实例持有会话及精确 stop 命令。若审查或检查阻塞，交付原因和证据，不启动实例、不声称通过。没有用户修复授权时只报告缺陷。

用户反馈对应当时 SHA；PR 更新后新 SHA 重新准备。旧实例仍是旧版，不复用旧人工批准。人工验收通过也不触发自动合并/部署。

## 新 Agent 接手与明确重试

先读 [任务记录](tasks/README.md)、相关 Issue/PR 和当前 Git 状态，再核对外置 plan/state、runId、检查轮次、源码指纹及交付结果。状态/工具输出可能含长日志，先读简要结果，不打印凭据。任务 Markdown 不覆盖程序状态。

终态 review/blocked 只读交接。用户明确要求重新执行后，宿主 Agent 调用 `ResumeTask -Issue N -Reason <实际原因>`，需求变化时追加 PlanFile；保留 history，再核对远端分支/草稿是否已部分发布并按手册入队。不得删除状态文件、换会话或反复加 ready 重置修复次数。没有明确重试请求时解释下一步，不自行恢复。

给下一位 Agent 的最小交接：用户目标与已授权操作、当前职责/阶段、Issue/PR 与完整 SHA、计划和状态位置、检查结果与证据、待人工确认项、正在运行的实例与停止方式、下一步具体操作。使用 [任务模板](tasks/template.md) 留存。

## 文档能被识别的前提

这些规则必须出现在 Agent 实际读取的检出目录。只读远端仓库、另一台机器或旧 worktree 的 Agent 看不到尚未提交/同步的修改；本机 `.local` 合同、凭据和运行证据也不会随 Git 自动迁移。缺少环境或合同应明确阻塞，不能沿用本机已安装的假设。

不自动读取 AGENTS.md 的工具，可直接给它：

> 先读取仓库根 AGENTS.md 和 docs/17-agent-workflow.md，说明当前应处于哪个阶段、由谁执行检查和交付，再按已授权范围工作。关键需求不明确时向我确认；不要自行入队、重试、合并或部署。

文档提供可发现、可执行的约定，不能保证所有模型都遵守。受控任务的检查轮次、持久化终态和字节发布由程序约束；需求理解、独立审查和人工观感仍需要对应负责人判断。
