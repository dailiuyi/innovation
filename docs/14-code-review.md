# Code Review 默认规则

当用户要求 review、审查代码或检查某次改动时，应用本页默认约定。用户本次明确指定的范围、重点和是否修复优先；无需每次重复整套规则。审查方法由 Agent 根据实际风险决定。

## 范围与依据

- “当前未提交的修改”包括暂存、未暂存及未被忽略的相关新增文件。先查看 Git 状态与实际 diff；只看 `git diff` 会漏掉暂存和新增文件。
- 用户点名的功能作为重点；其他未提交改动仍需识别并在结论中交代。明确限定了文件、提交或分支时按该范围审查，必要时阅读范围外的调用方，不扩大改动范围。
- 没有待审查改动或范围无法确定时说明情况并询问，不擅自把最近一次提交作为本次改动。无需为已有明确范围重复确认。
- 对照用户需求、验收、相关 spec/任务记录和已接受的架构约束阅读实际代码。实现 Agent 的总结与旧报告只作线索；需求未记录时说明推断，不虚构验收标准。
- 区分本次引入/暴露的缺陷、原有问题和待确认疑点。历史候选设计不自动构成新功能要求；已经明确接受的取舍不因个人偏好重新提出。若新证据表明取舍造成具体故障，应说明证据。

## 审查标准

优先检查需求遗漏、实际功能缺陷和回归。按改动追踪必要的上下游，关注相关接口、数据迁移、权限、事务、并发、幂等、失败恢复及审计；不要求每次逐项穷举。

问题应有具体触发条件、影响和代码依据。格式、命名或重构偏好不单独作为缺陷，除非违反明确约定并产生可说明的维护/正确性影响。不要为凑数量找问题，也不要仅因测试通过而判定业务正确。

## 验证与权限

优先按 [专项优先流程](16-fast-review.md) 运行最短需求路径，再按风险扩展。用户要求审查后人工验收时，无阻断问题后继续交付同版本隔离实例，不以“代码审查通过、网址待启动”结束。实例仅绑定回环，使用合成账号与隔离数据。

默认只审查，不修改业务代码、规范、任务记录或正式验收报告，不提交、不合并、不部署。只有用户同时要求修复时，才进入修改流程。运行检查可以产生忽略的本地日志和构建产物；不操作日常 Demo 数据或重启日常服务。

根据风险选择必要验证，使用 [Harness](13-harness.md) 的隔离入口，先查看已有证据是否对应本次代码。已有同版本且覆盖充分的结果可以复用，并说明来源；没有新改动、失败或具体疑点时不重复跑全量测试。只有结构或构建检查通过，不能当成完整业务验收。

启动时记录审查范围和版本；工作区存在未提交修改时不能仅以 HEAD 标识版本。结束前核对状态、相关 diff 或源码指纹；若编写 Agent 仍在修改，重新检查受影响部分，无法得到稳定版本时明确结论对应的快照和未覆盖内容。

缺环境、权限、登录或运行条件时记录阻塞，不算通过，不为满足验证而绕过权限或修改测试标准。直接运行旧验收脚本前核对副作用，避免其默认输出覆盖正式报告。

## 输出

先给出实质问题，按影响排序。每项注明文件与行号、触发条件、影响和简短修复方向；尚未确认的疑点单独标明，不包装成确定缺陷。

末尾简要说明审查范围、实际执行或复用的验证及未验证项。没有发现实质问题时直接说明，不强行提建议，也不保证不存在缺陷。结论只对应审查过的代码版本，不自动代表允许合并或发布。

## 日常提示示例

> 帮我 review 当前未提交的修改，主要是实现了场景发布功能。

这句话已足够启动上述流程；“场景发布”只是这次审查的重点。必要时补充本次特殊需求、明确接受的取舍或具体担忧，无需重复通用检查清单。项目功能状态以当前代码和功能文档为准，不由示例定义。
